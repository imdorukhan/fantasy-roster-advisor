# Minimal canonical staging issuer — P1 release lane

This branch starts at active production 564058b. It adds only the canonical issuer, a small route and the extracted existing owner verifier, tests, and a CI trigger. It does not include P2, receiver, DB migration, pool changes or cron changes. PR targets a pinned P1 release branch, NOT main (which already contains rolled-back P2). Do not merge into main or auto-promote.

Default disabled. Require canonical host, production read flags, enrolled owner metadata verification on GET and POST, exact Origin on POST, explicit consent, exact configured target host and deployment ID. The issuer must never enable receiver mode. The grant format remains compatible with PR #21. Only a separate owner-approved release and secure key provisioning may activate it.

## Key separation and replay
Generate a dedicated Ed25519 key pair only in approved secure infrastructure. Build the receiver with public SPKI DER only, no private key. Then configure the canonical issuer with PKCS8 DER private key and exact target. Never expose keys in logs or chat. Remove issuer settings before subsequent staged builds. No key provisioned by this change.
The signed grant is body-only, challenge-bound, expires after 300s, and handoff must occur within 60s. Stateless consent can reissue a grant for the same challenge, and possession of grant plus proof permits replay during its valid window. Ordinary browser exchange clears the pending proof; no durable single-use or immediate revocation guarantee. Strong atomic consumption requires shared state or a separately designed mechanism; do not add schema here.
The browser test harness uses a separate temporary HTTPS origin proxy, ephemeral Ed25519 keys and a synthetic owner session only. It imports the actual PR #21 receiver from the exact separately checked-out source. Never point the harness at real applications. No real cookie/token inspection. For actual staging rollout, verify top-level Form POST with SameSite policy and cross-site redirect Fetch Metadata; fail closed if browser blocks it. A second same-origin confirmation/landing step may be required in receiver code; this issuer-only branch does not change it.

## Browser fixture procedure
Checkout this exact hotfix in an isolated temporary directory. Extract the receiver file from PR #21 commit 8a901a9dba7543ef38150d6d88fc013fa0880606 separately (do not ship it in this hotfix). Run npm ci --ignore-scripts, then node scripts/stage-issuer-browser-check.mjs /path/to/fixture-receiver.mjs /path/to/Chrome. For Firefox and WebKit use an isolated test-only Playwright installation and browser binaries, set SC3_TEST_ENGINE and SC3_TEST_PLAYWRIGHT_MODULE to the engine and local absolute index.mjs path. The allowlisted loopback TLS proxy maps only the two fixture hosts; it never connects to real applications. Browser result distinguishes exchange HTTP 303 from redirected status and subsequent direct status. All key material is ephemeral in the fixture. Browser acceptance does not prove the real deployment-protection interaction.

## Observed fixture result
Chromium with default and third-party phaseout flag, and Firefox 135, successfully transfer the grant (303), then authorize direct staged status and allowlisted reads (200). The immediate redirect to status returns 401 before a direct navigation; this is a receiver acceptance-flow defect, not an issuer rejection. Writer and isolated browser context reads remain 401. WebKit 18.4 was blocked by the isolated loopback TLS fixture before reaching issuer code; no Safari compatibility claim. Do not weaken TLS or modify the user's trust store to pass a fixture. Receiver landing-page handling and real-browser compatibility must be resolved before live activation.

## Mandatory release window (v2 protocol)
Both issuer and receiver require identical SC3_STAGE_NOT_BEFORE and SC3_STAGE_NOT_AFTER canonical UTC Unix epoch seconds, with 0 < end-start <= 1800 seconds. Missing, malformed, future, reversed, oversized or expired windows fail closed. Build-time configuration is immutable per deployment; do not use now+1800 at cold start. The grant signs both bounds, caps expiry and handoff at end, and rejects old v1 grants and mismatched windows. Owner verification must finish before end. Normal owner access on canonical remains unchanged; the dedicated receiver host cannot fall back to a Yahoo session. After expiry new requests are rejected; in-flight reads already authorized can complete. Stateless replay remains possible with both proof and grant during their bounded lifetime. Rollback to pre-window code is NOT protected by this change: never enable earlier issuer/receiver deployments, verify they were never provisioned, and do not restore an enabled legacy deployment. Existing deployment settings cannot be revoked by editing project environment. Before activation separately authorize a window short enough to encompass both builds; if it expires before acceptance, abandon and rebuild both with a new matching window, never extend just one. No migration or actual key is required for CI.
