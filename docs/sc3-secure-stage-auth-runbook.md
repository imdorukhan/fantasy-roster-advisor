# Secure staging acceptance (disabled by default)

Scope: league 85892 read-only acceptance, exact unique Vercel deployment hostname and VERCEL_DEPLOYMENT_ID. No Yahoo session, token, GUID or existing cookie value is transferred. The existing canonical owner verifier remains required for approval. No migrations, cron, writer, paid resources or deployment protection changes.

## Two-phase rollout (separate authorization required)
1. Review this PR against PR #20 (the PR targets main for the existing CI; do not merge until PR #20 is reviewed). Run CI with ephemeral Ed25519 keys. Test disabled route on protected Preview. Do not enable issuer or receiver in this PR.
2. A future authorized canonical issuer-only release must preserve the current P1 code and existing authentication. Existing 564058b lacks the issuer. Deploy the issuer only, default off; verify P1 and rollback before any P2 release.
3. Provision a dedicated Ed25519 key pair in an approved secure environment. Build the receiver BEFORE adding the private key to production environment settings; the staged production build must contain only the public SPKI DER base64 key. Add the private PKCS8 DER base64 key only for the separately approved canonical issuer build. Remove the signing key and issuer configuration from project settings before any subsequent staged build. Existing deployments retain their build-time environment; use the exact deployment identities and verify the staged receiver never contains the signing key. Never print or transfer real keys in chat, never reuse Yahoo secrets. Do not put private key in a preview. The application uses no new DB tables.
4. Build exact staged production with SC3_STAGE_RECEIVER=1 and public key, SC3_P2_READ_ENABLED=1; keep canonical domain assignment disabled and Vercel Deployment Protection intact. Runtime VERCEL_URL and VERCEL_DEPLOYMENT_ID must be available and match exact URL. Set canonical issuer config SC3_STAGE_ISSUER=1, SC3_STAGE_TARGET_HOST and SC3_STAGE_TARGET_DEPLOYMENT_ID to that verified deployment; separate build to apply config. Do not grant arbitrary destination.
5. Owner opens staged /api/auto-data?sc3StageAuth=begin, navigates to canonical approval, explicitly consents using existing owner session, then submits form to the fixed staged host within 60 seconds. Browser's own pending proof must accompany the form. If third-party cookie policies block this form POST, fail closed; never copy cookies or weaken protection.
6. The status endpoint returns deployment ID, expiry and exact acceptance URLs. Verify each read within 5 minutes, including P1 rosters/scoreboard/streaming/player profiles and P2 lab/forecast. No grant for generic live endpoints, OAuth, jobs, writes or mixed query strings. This is a dedicated API acceptance capability, not a full Yahoo login or a way to test every canonical UI feature. Canonical owner Chrome UI checks still follow promotion if separately authorized.
7. Clear staged grant via same-origin POST to sc3StageAuth=clear; turn off issuer/receiver for future deployments. Grants are stateless, bound to two browser cookies and expire at five minutes; there is no durable single-use ledger or immediate server-side revocation. Clearing the pending proof prevents ordinary repeated browser exchange, but a replay with both credentials before expiry remains possible. Never claim stronger replay protection. A stage URL continues to be valid until expiry even if canonical alias is promoted; grant never works on canonical hostname.

If authorization or test fails, retain 564058b and no promotion. No change to current production or existing staged build is made by this branch.
