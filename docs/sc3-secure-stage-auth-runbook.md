Scope: league 85892 read-only acceptance, exact unique Vercel deployment hostname and VERCEL_DEPLOYMENT_ID. No Yahoo session, token, GUID or existing cookie value is transferred. 4. Build exact staged production with SC3_STAGE_RECEIVER=1 and public key, SC3_PRODUCTION_READS=1, SC3_SHARED_DB=1, SC3_P2_READ_ENABLED=1; receiver refuses Preview, isolated mode, issuer flag or any signing-key configuration. keep canonical domain assignment disabled and Vercel Deployment Protection intact. Runtime VERCEL_URL and VERCEL_DEPLOYMENT_ID must be available and match exact URL. Set canonical issuer config SC3_STAGE_ISSUER=1, SC3_STAGE_TARGET_HOST and SC3_STAGE_TARGET_DEPLOYMENT_ID to that verified deployment; separate build to apply config. Do not grant arbitrary destination.
5. Owner opens staged /api/auto-data?sc3StageAuth=begin, navigates to canonical approval, explicitly consents using existing owner session, then submits form to the fixed staged host within 60 seconds. The receiver returns a no-store 200 HTML landing document with a fixed same-origin status link. Click Continue to staged status; the new navigation must succeed without weakening Fetch Metadata checks. Browser's own pending proof must accompany the form. If third-party cookie policies block this form POST, fail closed; never copy cookies or weaken protection.
6. The status endpoint returns deployment ID, expiry and exact acceptance URLs. Verify each read within 5 minutes, including P1 rosters/scoreboard/streaming/player profiles and P2 lab/forecast. No grant for generic live endpoints, OAuth, jobs, writes or mixed query strings. This is a dedicated API acceptance capability, not a full Yahoo login or a way to test every canonical UI feature. Canonical owner Chrome UI checks still follow promotion if separately authorized.
7. Clear staged grant via same-origin POST to sc3StageAuth=clear; turn off issuer/receiver for future deployments. Grants are stateless, bound to two browser cookies and expire at five minutes; there is no durable single-use ledger or immediate server-side revocation. Clearing the pending proof prevents ordinary repeated browser exchange, but a replay with both credentials before expiry remains possible. Never claim stronger replay protection. A stage URL continues to be valid until expiry even if canonical alias is promoted; grant never works on canonical hostname.

If authorization or test fails, retain 564058b and no promotion. PR #22 P1-only issuer remains unchanged. No change to current production or existing staged build is made by this branch.

## Receiver finalization evidence

Original fixture Chrome traces: exchange cross-site/navigate/document -> 303, redirected status cross-site/navigate/document -> 401, direct status none -> 200. Fetch Metadata follows the entire redirect chain (https://www.w3.org/TR/fetch-metadata/). The new receiver commits an HTML document (200) instead of redirecting; its fixed same-origin link starts a fresh navigation. It contains no credential, scripts, external resources, or data. Status and data endpoints still reject cross-site requests, and now also reject same-site sibling requests when metadata is present. Cross-origin exchange remains exact canonical Origin only and requires navigate/document when metadata is supplied. Missing metadata is supported as before. Receiver configuration is production-only, public-key-only; both roles cannot be enabled in one runtime.

Actual isolated Chrome default and third-party-phaseout flag, and Firefox 135: exchange 200 (cross-site), link status 200 (same-origin), allowlisted read 200; cross-site status, wrong deployment, separate browser context, expired grant and writer query all 401. Expiry is tested by advancing a fixture-only server clock; no waiting or live keys. WebKit 18.4 failed TLS in the loopback fixture even with SAN certificate; not application acceptance evidence. Do not weaken TLS or modify system trust. The protected Preview must remain disabled; fixture acceptance is not proof of real Vercel protection/owner handoff.

## Replay without migration

- Existing mechanism: host-bound proof cookie, Ed25519 audience/deployment/scope signature, 60-second exchange window, 300-second expiry, pending proof deletion on success. Ordinary browser repeat exchange fails; captured original proof plus grant can still be reused before deadline. Clearing cookies is local logout, not global revocation.
- In-memory set / local cache: not safe as a global single-use mechanism across Vercel instances or cold starts. PostgreSQL advisory locks only protect simultaneous sessions, not consumed challenges after release; do not claim replay prevention.
- Existing approved shared atomic TTL store, if one exists: insert-if-absent (SET NX EX or equivalent) keyed by hash of challenge, with TTL covering entire validity; consume before accepting exchange; fail closed on store failure. No new resource provisioned or production writes authorized. Durable replay checks and early revocation need such shared state; no migration is necessary only if an approved store already supports it.
- Browser proof-of-possession key / per-request signature (RFC 9449 https://www.rfc-editor.org/rfc/rfc9449.html): reduces usefulness of a stolen bearer grant, but true one-time proof enforcement still needs shared state. Requires a separately reviewed protocol and browser support; not retrofitted here.
- Keep default off until real owner handoff, exact-deployment protection and risk acceptance are separately approved. Never transfer a signing key or owner session to the receiver.

Run the manual harness scripts/stage-receiver-browser-check.mjs with the exact extracted PR22 issuer module and a fresh Chrome executable, or isolated Playwright Firefox/WebKit module via SC3_TEST_ENGINE and SC3_TEST_PLAYWRIGHT_MODULE. No real endpoints accessed: allowlisted loopback proxy. Harness traces only Fetch Metadata and HTTP status. Node test autodiscovery intentionally excludes manual harness.

## Mandatory release window (v2 protocol)
Both issuer and receiver require identical SC3_STAGE_NOT_BEFORE and SC3_STAGE_NOT_AFTER canonical UTC Unix epoch seconds, with 0 < end-start <= 1800 seconds. Missing, malformed, future, reversed, oversized or expired windows fail closed. Build-time configuration is immutable per deployment; do not use now+1800 at cold start. The grant signs both bounds, caps expiry and handoff at end, and rejects old v1 grants and mismatched windows. Owner verification must finish before end. Normal owner access on canonical remains unchanged; the dedicated receiver host cannot fall back to a Yahoo session. After expiry new requests are rejected; in-flight reads already authorized can complete. Stateless replay remains possible with both proof and grant during their bounded lifetime. Rollback to pre-window code is NOT protected by this change: never enable earlier issuer/receiver deployments, verify they were never provisioned, and do not restore an enabled legacy deployment. Existing deployment settings cannot be revoked by editing project environment. Before activation separately authorize a window short enough to encompass both builds; if it expires before acceptance, abandon and rebuild both with a new matching window, never extend just one. No migration or actual key is required for CI.
